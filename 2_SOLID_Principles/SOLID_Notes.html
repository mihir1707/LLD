📖 What is SOLID?

SOLID is a set of 5 design principles introduced by Robert C. Martin (Uncle Bob) that help you write software that is easy to maintain, extend, and understand. Each letter stands for one principle. Together, they prevent your code from becoming a tangled mess.

🏠 Real-Life Analogy

Think of SOLID like the rules a good architect follows. SRP = one room has one purpose. OCP = add rooms without demolishing old ones. LSP = replace a light bulb with any compatible one. ISP = kitchen has only kitchen tools, not car tools. DIP = use a universal charger, not a device-specific wire.

🔧

Maintainable Code

Easy to fix bugs without breaking other parts.

🔄

Extensible Design

Add new features without touching existing working code.

🧪

Testable Units

Small, focused classes are easier to unit test.

👥

Team Friendly

Clear responsibilities = less merge conflicts and confusion.

S
Principle 1 of 5

Single Responsibility Principle

A class should have only one reason to change
📖 Definition

Every class should do exactly one thing and be responsible for only one part of the system. If your class has multiple reasons to change (e.g., business logic changes AND database changes), it violates SRP.

🏦 Real-Life Analogy

A Chef cooks food. A Waiter serves it. A Cashier collects payment. Each person has ONE job. If the chef also had to collect payment AND serve food AND cook — the kitchen would be chaotic. That's a God Class!

❌ Violation — God Class

Imagine a Ticket class that:

  • Stores ticket data (id, entry time, fee)
  • Calculates parking fee (business logic)
  • Saves itself to the database (DB logic)
  • Generates PDF receipt (formatting)

If tax rules change → edit Ticket. If DB changes → edit Ticket. If PDF format changes → edit Ticket. Too many reasons to change!

✅ Fix — Split Responsibilities
  • Ticket → only holds data
  • FeeCalculator → calculates fee
  • TicketRepository → saves to DB
  • ReceiptGenerator → makes PDF

Each class has one reason to change. Fee logic changes? Only touch FeeCalculator. DB changes? Only touch TicketRepository.

Vehicle_Parking.cpp — SRP in Action 
// ❌ VIOLATION: Ticket class doing too many things
// Bad: Ticket holds data + calculates fee + saves to DB
class BadTicket {
    void calculateFee()  { /* tax logic */ }  // ← NOT ticket's job
    void saveToDatabase() { /* DB code */ }   // ← NOT ticket's job
};                                                   // 3 reasons to change!

// ✅ FIX: Each class has ONE job
class Ticket {              // ← Only stores ticket data
public:
    string ticketId;
    Vehicle* vehicle;
    ParkingSpot* spot;
    int entryTime;           // That's it! No fee calc, no DB
};

class PaymentStrategy {     // ← Separate class for fee calculation
public:
    virtual double calculateFee(Ticket* t) = 0;
    virtual void pay(double amount) = 0;
};

// ParkingLot delegates — doesn't do everything itself
class ParkingLot {
    SpotAllocationStrategy* allocation; // delegates spot finding
    PaymentStrategy* payment;           // delegates payment
};
Google_Docs.cpp — SRP: Document vs Persistence 
// Document class has ONE job: hold and render elements
class Document {                 // ← only manages content
    vector<DocumentElement*> elements;
    string render();               // render to string - that's it!
};

// Persistence class has ONE job: saving
class Persistence {             // ← only knows about saving
    virtual void save(string data) = 0;
};

// DocumentEditor orchestrates — but delegates actual work
class DocumentEditor {          // ← only manages user interactions
    Document* document;         // delegates rendering to Document
    Persistence* storage;       // delegates saving to Persistence
};
💡 Quick Rule

Ask yourself: "How many reasons does this class have to change?" If the answer is more than 1, you're violating SRP. Split it up!

O
Principle 2 of 5

Open/Closed Principle

Open for extension, closed for modification
📖 Definition

You should be able to add new functionality (extend) without changing existing working code (modify). Add new behavior by adding new classes — not by editing old ones.

🏭 Real-Life Analogy

Think of a smartphone. You can install new apps (extend functionality) without modifying the phone's hardware or OS (no modification). The phone is closed for modification (you can't change the chip) but open for extension (install any app).

❌ Violation — if/else hell

One massive ParkingSpot class with if-else:

if (type == COMPACT)     { ... }
else if (type == LARGE)  { ... }
else if (type == MOTOR)  { ... }
// Add ElectricSpot? Must EDIT this!

Changing existing code = risking new bugs.

✅ Fix — Polymorphism
class ParkingSpot { virtual canFitVehicle() = 0; }
class CompactSpot : ParkingSpot { ... }
class LargeSpot   : ParkingSpot { ... }
class ElectricSpot: ParkingSpot { ... }  // NEW!

Add ElectricSpot? Just create a new class. Zero changes to existing code!

Vehicle_Parking.cpp — OCP with Abstract ParkingSpot 
// Base class — CLOSED for modification (don't touch this)
class ParkingSpot {                 // abstract base
public:
    virtual bool canFitVehicle(Vehicle* v) = 0; // define the contract
    void occupy(Vehicle* v)  { vehicle = v; isOccupied = true; }
    void vacate()             { vehicle = nullptr; isOccupied = false; }
};

// OPEN for extension — add new spot types by creating new classes
class CompactSpot : public ParkingSpot {  // NEW class, no edits to base
public:
    bool canFitVehicle(Vehicle* v) override {
        return (v->type == CAR || v->type == BIKE);
    }
};

// Tomorrow, add ElectricSpot — zero changes to existing code!
class ElectricSpot : public ParkingSpot { // just add new class
public:
    bool canFitVehicle(Vehicle* v) override {
        return v->isElectric; // new logic, old code untouched
    }
};

// SpotAllocationStrategy also follows OCP
class SpotAllocationStrategy {         // closed base
    virtual ParkingSpot* findSpot(...) = 0;
};
class FirstAvailableSpot : public SpotAllocationStrategy { /* open extension */ };
class NearestExitSpot   : public SpotAllocationStrategy { /* add new strategy */ };
💡 Quick Rule

"Can I add new behavior without touching existing classes?" If yes → OCP satisfied. The magic tool is abstraction + polymorphism — use virtual/abstract base classes and add new concrete classes for new behavior.

L
Principle 3 of 5

Liskov Substitution Principle

Subtypes must be substitutable for their base types
📖 Definition

If class B is a subclass of class A, then anywhere you use A, you should be able to use B without breaking the program. The child class must behave correctly wherever the parent is used — no surprises!

🔌 Real-Life Analogy

Any USB charger should work in any USB port. If you buy a "USB charger" (subtype of Charger), it should charge your phone correctly — it shouldn't explode or do nothing. If a subclass behaves unexpectedly, it violates LSP. Like buying a "charger" that only works on Tuesdays — that's a bad subtype!

📓 From Your Notes — The 3 LSP Rules

📝 Signature Rule

The child class must have the same method signatures as the parent. Three sub-rules:

→
Method Assignment (Contravariance of parameters) Child can accept same or broader parameter types than parent. Never narrower.
→
Return Type (Covariance of return) Child can return same or more specific type than parent. Never broader.
→
Exception Rule Child can only throw same or fewer/narrower exceptions than parent. Never new unexpected ones.
🏗️ Property Rule

The child class must maintain the same state rules as the parent. Two sub-rules:

→
Class Invariant Any condition that was always true in the parent must still be always true in the child.
e.g.: balance must always be ≥ 0 in BankAccount — child SavingsAccount must also maintain this.
→
History Constraint If parent only allows state changes in certain ways, child cannot allow new forbidden state changes.
e.g.: If parent says "can't change ID after creation", child must also not allow it.
⚙️ Method Rule

Each method in the child must respect the parent's behavior contract. Two sub-rules:

→
Pre-condition (Weaken or same) Child method can only have weaker or equal pre-conditions than parent. Never stricter.
If parent's deposit() accepts amount ≥ 0, child can't demand amount ≥ 100.
→
Post-condition (Strengthen or same) Child method must produce same or stronger guarantees than parent. Never weaker.
If parent guarantees withdraw() reduces balance by exactly the amount, child must too.
❌ Violation — Bike has turnOnAC()
class Vehicle {
  virtual void turnOnAC();  // on parent
};
class Bike : Vehicle {
  void turnOnAC() {
    throw "Bikes have no AC!";
  }  // ❌ LSP broken!
};
Using Vehicle* v = new Bike();
v->turnOnAC(); // CRASH! Surprise!
✅ Fix — Use canFitVehicle() check
// Vehicle only has what ALL vehicles do
class Vehicle {
  string licensePlate;
  VehicleType type;  // common to all
};
// Bike IS-A Vehicle safely
class Bike : Vehicle {};  // no fake methods!
// Spot validates compatibility
bool canFitVehicle(Vehicle* v) {
  return v->type == BIKE || v->type == CAR;
}
Vehicle_Parking.cpp — LSP Applied Correctly 
// ✅ Vehicle class has ONLY what's common to ALL vehicles
class Vehicle {
public:
    string licensePlate;    // all vehicles have this
    VehicleType type;       // all vehicles have this
    // NO turnOnAC(), NO playMusic() — bike would break LSP!
};

// ✅ Car is-a Vehicle — no surprises, no fake methods
class Car : public Vehicle {
public:
    Car(string plate) : Vehicle(plate, VehicleType::CAR) {}
    // Car can add extra things (like turnOnAC) in its OWN class
};

// ✅ Bike is-a Vehicle — substitutable anywhere Vehicle* is used
class Bike : public Vehicle {
public:
    Bike(string plate) : Vehicle(plate, VehicleType::BIKE) {}
};

// Anywhere Vehicle* is used, Car* or Bike* works perfectly
Vehicle* v = new Car("GJ-01-XX-9999");
myLot.parkVehicle(v); // works! No crash, no surprise

v = new Bike("MH-02-YY-1111");
myLot.parkVehicle(v); // works! Bike substitutes Vehicle
💡 Quick Rule

"Can I replace the parent with a child without the program breaking or behaving unexpectedly?" If a child class throws exceptions the parent doesn't, or refuses to do what the parent promised — LSP is broken.

I
Principle 4 of 5

Interface Segregation Principle

No class should be forced to implement methods it doesn't use
📖 Definition

Instead of one fat, bloated interface with many methods, split it into smaller, focused interfaces. A class should only implement the methods it actually needs — not be forced to implement useless ones.

🍽️ Real-Life Analogy

Imagine a restaurant menu with everything: pizza, sushi, burgers, cocktails, desserts. A customer who's vegetarian doesn't need the meat section. ISP says: have a Veg Menu, Drinks Menu, Dessert Menu separately. Don't force a vegetarian to scroll through meat items!

❌ Violation — Bloated Interface
class PaymentInterface {
  virtual void calculateFee() = 0;
  virtual void pay() = 0;
  virtual void issueCreditRefund() = 0; // ???
  virtual void applyCrypto() = 0;       // ???
};
class CashPayment : PaymentInterface {
  void issueCreditRefund() {
    throw("Cash can't refund!"); // ❌
  }
};
✅ Fix — Small, Focused Interfaces
class IFeeCalculator {
  virtual double calculateFee() = 0;
};
class IPayable {
  virtual void pay(double amount) = 0;
};
// CashPayment only needs these two
class CashPayment
  : IFeeCalculator, IPayable {
  // implements only what it needs!
};
Vehicle_Parking.cpp — ISP: Clean PaymentStrategy Interface 
// ✅ PaymentStrategy interface is focused — only 2 methods
class PaymentStrategy {
public:
    virtual double calculateFee(Ticket* t) = 0;
    virtual void   pay(double amount) = 0;
    // No issueCreditRefund() here — that would be ISP violation!
};

// CashPayment only implements what it actually can do
class CashPayment : public PaymentStrategy {
public:
    double calculateFee(Ticket* t) override { return 10.0; }
    void   pay(double amount)       override { cout << "Cash: $" << amount; }
    // No fake issueCreditRefund() that throws an exception!
};

// Google Docs example — DocumentElement is focused
class DocumentElement {
    virtual string render() = 0;  // ONE method — ISP satisfied
};
💡 Quick Rule

"Is any class implementing a method it doesn't use, or leaving it blank/throwing?" If yes → split that interface into smaller pieces. Clients should only depend on methods they actually call.

D
Principle 5 of 5

Dependency Inversion Principle

Depend on abstractions, not on concrete implementations
📖 Definition

High-level modules (like ParkingLot) should not depend directly on low-level modules (like CashPayment). Both should depend on an abstraction (interface). This is called "inverting" the dependency.

🔌 Real-Life Analogy

Your laptop has a USB port (abstraction). You can plug in any USB device — keyboard, mouse, speaker, flash drive (concrete implementations). The laptop doesn't know or care which specific device is plugged in. This is DIP! If the laptop had a built-in Sony keyboard (hardcoded), it can't be replaced = DIP violation.

❌ Violation — Hardcoded dependency
class ParkingLot {
  private:
    // ❌ Directly uses concrete class!
    CashPayment payment;     // hardcoded
    FirstAvailable alloc;   // hardcoded

  ParkingLot() {
    payment = new CashPayment(); // ❌
    alloc = new FirstAvailable(); // ❌
  }
};
Want UPI payment? Must EDIT ParkingLot!
✅ Fix — Inject abstractions
class ParkingLot {
  private:
    // ✅ Depends on interfaces!
    SpotAllocationStrategy* alloc;
    PaymentStrategy* payment;

  ParkingLot(
    SpotAllocationStrategy* a,
    PaymentStrategy* p) { // injected!
    alloc   = a;
    payment = p;
  }
};
Swap UPI in without editing ParkingLot!
Vehicle_Parking.cpp — DIP: Constructor Injection 
// ✅ ParkingLot depends on ABSTRACTIONS (interfaces), not concrete classes
class ParkingLot {
    vector<ParkingSpot*> spots;           // abstraction
    SpotAllocationStrategy* allocation;  // interface, not FirstAvailableSpot*
    PaymentStrategy* payment;            // interface, not CashPayment*

public:
    // Injected from outside! ParkingLot doesn't create them.
    ParkingLot(vector<ParkingSpot*> s,
               SpotAllocationStrategy* alloc,
               PaymentStrategy* pay) {
        spots = s; allocation = alloc; payment = pay;
    }
};

// In main() — you decide WHICH concrete class to inject
SpotAllocationStrategy* allocator = new FirstAvailableSpot();
PaymentStrategy* payment = new CashPayment();
ParkingLot myLot(spots, allocator, payment);

// Tomorrow: switch to UPI — zero changes to ParkingLot!
PaymentStrategy* payment = new UPIPayment();   // just change here
ParkingLot myLot(spots, allocator, payment);    // ParkingLot unchanged!
Google_Docs.cpp — DIP: DocumentEditor depends on Persistence interface 
// ✅ DocumentEditor depends on Persistence INTERFACE — not FileStorage directly
class DocumentEditor {
    Document*    document;  // abstraction
    Persistence* storage;   // interface, not FileStorage!

public:
    DocumentEditor(Document* doc, Persistence* store) {
        document = doc;  storage = store;  // injected!
    }
};

// In main() — decide storage type
Persistence* persistence = new FileStorage();    // or DBStorage()
DocumentEditor* editor = new DocumentEditor(doc, persistence);
// Switch to DB: new DBStorage() — DocumentEditor is untouched!
💡 Quick Rule

"Does my high-level class use new ConcreteClass() inside it?" If yes → DIP violation. Move that new to the outside (constructor injection, factory, or DI container) and have the class depend on an interface instead.

📓 LSP Sub-Rules — From Your Notebook

📝 Signature Rule

  • Method Assignment — Parameters: same or broader
  • Return Type — Return: same or more specific
  • Exception — Same or fewer exceptions thrown

🏗️ Property Rule

  • Class Invariant — Parent's always-true conditions still hold in child
  • History Constraint — Child can't allow state changes parent forbids

⚙️ Method Rule

  • Pre-condition — Child's input requirement: weaker or same
  • Post-condition — Child's output guarantee: stronger or same

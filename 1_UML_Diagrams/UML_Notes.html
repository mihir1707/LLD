What is UML?

Unified Modeling Language — the blueprint language for software

📖 Definition

UML (Unified Modeling Language) is a standardized visual language used to design, plan, and communicate the structure and behavior of a software system. It's like an architect's blueprint — before building a house, you draw it first.

🏠 Real-Life Analogy

Imagine you're building a shopping mall. Before laying a single brick, architects draw floor plans, electrical diagrams, and plumbing maps. UML is exactly that for software — diagrams that show how classes are connected, how they talk to each other, and what data they hold.

🎯

Why Use UML?

Visualize your system before writing code. Spot design problems early when they're cheap to fix.

👥

Team Communication

A picture says 1000 lines of code. UML helps developers, architects, and managers share a common understanding.

📚

Documentation

UML diagrams serve as living documentation that describes how your system is built and how it behaves.

🛠️

LLD Foundation

Every Low-Level Design problem starts with a UML diagram — class diagram for structure, sequence for flow.

🗂️ Types of UML Diagrams

Class Diagram

Shows the static structure — what classes exist and how they relate

📖 Definition

A Class Diagram represents the structure of a system by showing classes, their attributes (data), methods (behavior), and the relationships between them. It's a snapshot of your code structure — before writing a single line of code.

🏦 Real-Life Analogy — Bank System

Think of classes as departments in a bank. The Account department has data (balance, account number) and actions (deposit, withdraw). The Customer department has a customer linked to one or many accounts. The class diagram shows these departments and their connections.

🏗️ Anatomy of a Class Box

Every class in UML is drawn as a rectangle split into 3 sections:


BankAccount
-accountNumber : String
-balance : double
-owner : String
+deposit(amount : double)
+withdraw(amount : double) : bool
+getBalance() : double
#validate() : bool
  • Section 1 (Top) — Class Name (bold, centered)
  • Section 2 (Middle) — Attributes / Fields (data the class holds)
  • Section 3 (Bottom) — Methods / Operations (what the class can do)
  • Format: accessModifier name : type

🏦 Think of it as

A bank form: header = account type name, middle = your info (name, balance), bottom = what you can do (deposit, withdraw).

🔑

Access Modifiers

Who can see what — the visibility rules in UML

📖 Definition

Access modifiers define who can access an attribute or method. In UML, they are represented by a single symbol before the name.

🏠 Analogy — Rooms in a House

Think of a house: Public (+) = front door / living room (anyone can enter). Private (-) = your bedroom (only you). Protected (#) = family rooms (family members only). Package (~) = within the building/apartment complex.

Symbol Name Who Can Access Real-Life Example
+ Public Everyone (any class) Hotel lobby — open to all guests
- Private Only the class itself Your safe — only you know the PIN
# Protected Class + its subclasses (children) Family diary — you and your kids can read
~ Package Classes in same package Office intranet — only employees can access

Class Types in UML

Not all classes are the same — 4 special types you must know

Regular

Concrete Class

Car
-brand : String
-speed : int
+drive()

A normal, fully implemented class. You can create objects from it directly.

🚗 Example: Car, BankAccount, Student — all real things you can "make"
Abstract

Abstract Class

«abstract»
Vehicle
#speed : int
+drive()

Has at least one abstract (unimplemented) method. Cannot be instantiated directly — needs a child class.

🚌 Example: Vehicle is abstract — Car, Bus, Bike implement drive() differently. Shown with «abstract» or italic method names.
Interface

Interface

«interface»
Payable
+pay(amount : double)
+getReceipt() : String

A pure contract — only method signatures, no implementation. All methods are public by default. A class "implements" it.

💳 Example: Payable interface — CashPayment, UPIPayment, CardPayment all implement it differently.
Enum

Enumeration

«enumeration»
OrderStatus
PENDING
CONFIRMED
DELIVERED
CANCELLED

A fixed list of named constants. Used when a variable can only hold one of a few specific values.

🛒 Example: OrderStatus in Zomato — only PENDING, CONFIRMED, DELIVERED, or CANCELLED.

⚔️ Abstract Class vs Interface — Key Difference

FeatureAbstract ClassInterface
Has constructor?✅ Yes❌ No
Has fields/variables?✅ Yes❌ No (only constants)
Has implementation?✅ Partial (some methods)❌ None (pure contract)
Multiple inheritance?❌ No (one parent only)✅ Yes (implement many)
Access modifiers?✅ Any (+, -, #)✅ Public only by default

Relationships in Class Diagram

How classes connect to each other — 6 types with arrows

📖 Why Relationships?

Classes never live in isolation — they talk to each other. Relationships define HOW they are connected — does one own the other? Does one use the other? Does one inherit from another?

1

Association

A ──────────────→ B

Loose connection — A uses B, but neither owns the other. Both can exist independently.

👨‍🏫 Teacher teaches Students — Teacher and Student exist independently, just connected.
Arrow: Solid line, open arrowhead
2

Aggregation

A ◇──────────────→ B

"Has-A" (weak) — A has B, but B can exist without A. It's a "whole-part" relationship, but parts survive if whole is destroyed.

🏫 School has Teachers — if School closes, Teachers still exist and can work elsewhere.
Arrow: Solid line, hollow diamond at the "whole" side
3

Composition

A ◆──────────────→ B

"Has-A" (strong) — A owns B completely. B cannot exist without A. If A is destroyed, B is destroyed too.

🏠 House has Rooms — if House is demolished, Rooms no longer exist. Room can't survive without House.
Arrow: Solid line, filled diamond at the "owner" side
4

Inheritance (Generalization)

Child ───────────▷ Parent

"Is-A" relationship — Child class inherits all attributes and methods of the parent. Child is a more specific version of the parent.

🐾 Dog is-a Animal, Car is-a Vehicle, SavingsAccount is-a BankAccount — inherits all parent behavior.
Arrow: Solid line, hollow triangle arrowhead pointing to parent
5

Realization (Implementation)

Class - - - - - - ▷ «interface»

Class implements an Interface — the class promises to provide all methods defined in the interface (the contract).

💳 CashPayment implements Payable interface — Cash class must implement pay() and getReceipt().
Arrow: Dashed line, hollow triangle arrowhead
6

Dependency

A - - - - - - - -→ B

Weak, temporary use — A uses B briefly (as a parameter or local variable), but doesn't hold a permanent reference to it.

🧾 Order depends on PaymentService to process payment — it uses it temporarily, not a permanent relationship.
Arrow: Dashed line, open arrowhead

🔢 Multiplicity (Cardinality) — How Many?

Numbers on the ends of relationship lines show how many instances are involved on each side.


NotationMeaningReal-Life Example
1Exactly oneOne person has one passport
0..1Zero or one (optional)A person may or may not have a car
* or 0..*Zero or moreA teacher teaches 0 or many students
1..*One or moreAn order must have at least 1 item
m..nBetween m and nA team has 5..11 players

Full Class Diagram Example — Parking Lot System

Here's your actual Parking Lot class diagram — let's read it using all the notations we learned:

📁 ClassDiagram.png — Parking Lot System

Reading this diagram:

  • ParkingLot (Concrete Class) — has private fields: spots list, allocationStrategy, paymentStrategy
  • Vehicle («abstract») — Car, Bike, Truck inherit (is-a) from it
  • ISpotAllocationStrategy («interface») — FirstAvailableSpotStrategy implements (realizes) it
  • IPaymentStrategy («interface») — CashPayment, CreditCardPayment implement it
  • ParkingLot ◆→ Ticket — Composition: Ticket can't exist without ParkingLot
  • SpotType, VehicleType — «enumeration» with fixed values like COMPACT, LARGE, CAR, BIKE

💡 Aggregation vs Composition — The Easiest Way to Remember

◇ Aggregation — "Can Survive Alone"

Library has Books. If Library burns down, the books (data) still exist elsewhere. Parts are independent.

◆ Composition — "Dies Together"

Human has a Heart. If Human dies, the Heart stops existing as a functioning organ. Parts can't exist alone.

Sequence Diagram

Shows the dynamic behavior — how objects interact over time

📖 Definition

A Sequence Diagram shows the order of interactions between objects in a system over time. It focuses on who calls whom, when, and in what order. Think of it as a script/screenplay of your system's story.

🍕 Real-Life Analogy — Ordering on Zomato

You (User) open the app → Zomato shows restaurants → You place an order → Restaurant receives it → Delivery partner picks up → You get the food. This step-by-step time-ordered flow is exactly what a Sequence Diagram shows!

⏱️

Time Flows Downward

Top of diagram = beginning. Bottom = end. Read sequence diagrams top to bottom like a story.

↔️

Horizontal = Communication

Arrows going left/right between participants show messages being sent between them.

📋

Complements Class Diagram

Class diagram = structure (WHAT). Sequence diagram = behavior (HOW). Together they tell the full story.

🧩

Sequence Diagram Elements

Every building block — participants, lifelines, messages, fragments

👤 Participants (Actors & Objects)

Participants are shown at the top of the diagram as boxes or actors. Each one has a vertical dashed line called a Lifeline going down.


🧍
Client
(Actor / Human User)
OrderService
Object / Class
(Rectangle box)
PaymentService
Object / Class
Database
System / Component
↑ Each box has a dashed vertical line (lifeline) going down through the diagram
  • Stick figure / actor → human user or external system
  • Rectangle box → an object or class in your system
  • Dashed vertical line → lifeline (the participant's timeline)
  • Thick box on lifeline → activation bar (when the object is actively doing something)

✉️ Message Types (Arrows)

Arrows between participants represent messages / method calls. Different arrow styles = different types of calls.


1

Synchronous Call

A ──────────────▶ B

Caller waits for the response before doing anything else. Like calling someone on the phone — you wait for them to pick up.

🏦 User → BankSystem: deposit(5000) — user waits for confirmation
Arrow: Solid line, filled arrowhead
2

Return Message

A ◀ - - - - - - - B

Response going back to the caller. The reply to a previous synchronous call.

🏦 BankSystem → User: returns "Success" after deposit
Arrow: Dashed line, open arrowhead going back
3

Asynchronous Call

A ──────────────⇒ B

Caller sends message and does NOT wait — continues doing other things. Fire and forget.

📧 System sends email notification — doesn't wait for user to read it
Arrow: Solid line, half-open arrowhead
4

Self-Call (Recursive)

A ──→ A (curves back)

An object calling its own method. Arrow goes out and curves back to the same object.

🔄 Validator calls validate() on itself to check internal state
Arrow: Loops back to same lifeline

📦 Combined Fragments (Control Flow)

Fragments are rectangular frames that show conditional logic, loops, and alternatives — like if/else and for-loop in diagrams.


alt

Alternative (alt)

Like an if-else statement. The dashed line inside divides conditions. Only ONE branch executes.

💳 [Payment Success] → show receipt
- - - - - - - - - - -
[Payment Failed] → show error
opt

Optional (opt)

Like an if (without else). The messages inside only happen if the condition is true.

🎁 [User is premium] → apply discount. If not premium, nothing happens.
loop

Loop (loop)

Shows a repeating sequence. Like a for/while loop in code.

🛒 [for each item in cart] → add to order. Repeats until all items processed.
ref

Reference (ref)

Points to another sequence diagram. Used to keep diagrams clean by extracting complex flows.

📎 ref: Authentication Flow — reuses the login diagram without repeating it.
par

Parallel (par)

Shows concurrent / parallel execution. Multiple things happen at the same time.

⚡ Send email AND send SMS notification simultaneously — both happen at once.
break

Break (break)

Breaks out of the current flow when a condition is met. Like a break/return in code.

🚨 [Account locked] → break — stop current login flow immediately.

⬛ Activation Bar (Execution Box)

A thin rectangle on the lifeline that shows when an object is actively executing (processing a request). Appears when a method is being run and disappears when it returns.

💡 Analogy

Think of it like a busy indicator. When your phone is actively loading a page, a spinner shows. The activation bar is that spinner — it shows the object is working right now.

Reading a Sequence Diagram

Walk through the Parking Lot sequence diagram step by step

📁 SequenceDiagram.png — Parking Lot: Park & Unpark Flow
📖

Step-by-Step Reading — parkVehicle() Flow

  1. Client → ParkingLot: parkVehicle(vehicle) — User calls the park method with their vehicle.
  2. ParkingLot → ISpotAllocationStrategy: findSpot(spots, vehicle) — ParkingLot asks the strategy to find an available spot.
  3. [alt] Spot found: Strategy returns a ParkingSpot back to ParkingLot.
  4. ParkingLot → ParkingSpot: occupy(vehicle) — The spot is marked as occupied.
  5. ParkingSpot → Ticket: create Ticket — A new Ticket is created for this parking session (Composition!).
  6. ParkingLot → Client: returns the Ticket — User gets their parking ticket.
  7. [alt] No spot available: Returns null, Client gets NoSpotAvailableException.
📖

Step-by-Step Reading — unparkVehicle() Flow

  1. Client → ParkingLot: unparkVehicle(ticket) — User returns with their ticket to leave.
  2. ParkingLot → IPaymentStrategy: calculateFee(ticket) — Calculates the parking fee from the ticket's entry/exit time.
  3. IPaymentStrategy → ParkingLot: returns fee amount.
  4. ParkingLot → IPaymentStrategy: pay(fee) — Processes payment.
  5. [alt] Payment Successful: vacate() called on ParkingSpot → spot becomes available again → Client gets Receipt.
  6. [alt] Payment Failed: Returns failure → Client gets Payment Failed message.
📁 Diagrams.png — Full Overview: Class + Sequence Diagram Together

🔍 Key Observations from the Diagrams

  • The Class Diagram shows what objects exist (ParkingLot, Vehicle, Ticket, etc.) and their relationships
  • The Sequence Diagram shows HOW those same objects communicate during parkVehicle and unparkVehicle operations
  • The Composition (◆) between ParkingLot and Ticket in class diagram = reflected in sequence where Ticket is created inside parkVehicle
  • The «interface» ISpotAllocationStrategy and IPaymentStrategy in class diagram = appear as participants in sequence diagram
  • alt fragments in sequence = if-else handling for "spot found/not found" and "payment success/failure"

Class Diagram vs Sequence Diagram

Two sides of the same coin — structure vs behavior

Feature 📦 Class Diagram 🔄 Sequence Diagram
FocusStructure (WHAT exists)Behavior (HOW it works)
ShowsClasses, attributes, methods, relationshipsMessages, method calls, order of execution
Time dimension❌ Static (no time)✅ Dynamic (time flows top→bottom)
When to useDesign the data model and architectureDesign the flow for a specific use case
Analogy📋 A floor plan of a building🎬 A script/screenplay of what happens in the building
Main elementsClasses, interfaces, enums, arrowsParticipants, lifelines, messages, fragments
In LLDDraw first — shows all classes neededDraw after — shows how classes interact
